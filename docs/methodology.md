# Methodology

## Research context

Hugging Face's multi-harness RL guide describes training against verifiable tasks through the real harness so its tools, prompt construction, and control flow shape the rollouts. The subsequent Harness Hub work evaluated per-harness LoRAs, including LFM3-1.7B with Pi, on SmolDataEnvs and environments derived from coding trajectories. The later at-scale work applied the approach to Qwen3.8-27B and broader software-engineering tasks using TRL's asynchronous GRPO trainer. [Multi-harness RL guide](https://huggingface.co/spaces/FineEnvs/multi-harness-rl) · [Earlier harness adapters](https://huggingface.co/blog/harness-hub/harness-adapters) · [Harness adapters at scale](https://huggingface.co/blog/harness-adapters-at-scale)

This repository follows the upstream recipe of collecting exact sampled tokens in the target harness, scoring with executable verifiers, rewarding tool efficiency on successes, and optimizing LoRA weights with group-relative advantages. Its contribution is a native Apple Silicon implementation. Local MLX serves the model and updates the adapter sequentially, with offline ARM64 environments for rollouts. The reported experiment is a single-machine study with its own smaller SmolDataEnvs selection. [Upstream LFM3 Pi adapter](https://huggingface.co/harness-hub/LFM3-1.7B-pi) · [SmolDataEnvs](https://huggingface.co/datasets/FineEnvs/SmolDataEnvs-harbor-train) · [Harness Hub trajectory-derived environments](https://huggingface.co/datasets/harness-hub/traj2envs-rl) · [TRL AsyncGRPO implementation](https://huggingface.co/docs/trl/en/async_grpo_trainer)

## Rollouts and rewards

Pi and OpenCode run as installed agents inside Harbor's Linux ARM64 Docker environments. The runner requires Harbor's `no-network` policy, checks that the live container's Docker network mode is `none`, and forwards the harness's loopback model requests over `docker exec` stdio to the host-side inference endpoint. Task images contain the harness and its dependencies before rollout. Harbor runs the verifier after the session. [Harbor integration](../src/apple_harness_adapter/harbor.py)

OpenEnv's Harbor integration captures the session. At each model request the local endpoint applies the model's chat template, samples with MLX at the configured temperature, and records the exact prompt IDs, completion IDs, and behavior log probabilities of the sampled tokens. The gradient scorer uses those IDs directly. It predicts completion tokens from the prompt and preceding completion tokens, and excludes prompt positions from the loss. Each model request is scored independently because a later harness prompt can rewrite history. The runner checks completion masks and trainable token totals before optimizing. [Sampling and scoring](../src/apple_harness_adapter/backends/base.py) · [Trace schema](../src/apple_harness_adapter/trace.py)

The recorded experiments used SafeAgents in enforce mode. The proxy reviews declared tool calls before execution, filters blocked calls from the harness response, and records verdicts alongside the trajectory. Any enforced block makes the rollout's effective reward zero. Detector errors invalidate the attempt. Tool calls are counted as recorded invocations on retained agent turns. For other rollouts, effective reward equals the verifier score in `[0, 1]`, plus `0.1 × max(0, 1 − tool_calls / 15)` only when the verifier score is exactly 1. [SafeAgents review](../src/apple_harness_adapter/safe_agents.py) · [Reward implementation](../src/apple_harness_adapter/trace.py)

## Sequential on-policy optimization

For each task the runner collects a group of attempts with fixed policy weights. It subtracts the group's mean effective reward from each attempt's reward and divides by the sample standard deviation plus `1e-4`. A group with all equal rewards skips the update. For other groups, the runner accumulates gradients over each request in each rollout. It averages over completion tokens within each rollout and gives each rollout equal weight in the group. It clips the global gradient norm to 1 when needed, applies one Adam step to the LoRA matrices, and records the pre-clip norm and maximum absolute adapter deltas. [GRPO implementation](../src/apple_harness_adapter/grpo.py)

At a sampled token with current rescored log probability `ℓ`, the ratio in the GRPO-style surrogate is `exp(ℓ − stop_gradient(ℓ))`. The forward value is exactly 1 because the two operands have the same numeric value. Only the first operand carries gradients, so the derivative of the ratio with respect to `ℓ` is 1 at that point. The loss therefore supplies the local advantage-weighted policy gradient. Each group is used for a single update at its collection weights, and the ratio stays inside the `[0.8, 1.2]` clipping interval. The clipping branch is effectively inactive under this schedule. The recorded behavior log probabilities are used for consistency checks. There is no reference-policy KL penalty or rollout reuse across optimizer steps.

### Log-probability drift

The standard scorer measures the maximum absolute token log-probability difference from the recorded behavior values, in nats. If the full-sequence score exceeds the tolerance, the runner replays sampling's cached prompt and one-token decoding shapes. Training aborts if the accepted check is nonfinite or still exceeds the tolerance. When that replay passes, gradients still come from the full-sequence pass. The check can verify that the recorded probabilities agree with sampling-shaped replay while the actual gradient scorer exhibits larger numerical drift. The run logs both maxima and the number of replayed turns. Main training used a `0.2`-nat tolerance, logged 1,044 replayed turns, and recorded maximum raw and accepted differences of 1.4781 and 0.1995 nats, respectively. [GRPO implementation](../src/apple_harness_adapter/grpo.py) · [Per-group measurements](../results/lfm3-pi/training.jsonl)

### Model-specific paths

- **LFM3.** The local model implementation supports the hybrid convolution/attention decoder and the published checkpoint layout. The reference run used rank 32 LoRA, scale 2 (alpha 64), and zero dropout across the 153 decoder linear projections, including the convolution projections. The chat backend handles LFM3's thinking prefix and structured tool-call parsing. [LFM3 backend](../src/apple_harness_adapter/backends/lfm3.py) · [Model implementation](../src/apple_harness_adapter/backends/lfm3_model.py)
- **Qwen3.** The backend uses MLX-LM's Qwen3 model, renders the model's chat template, parses JSON tool calls, and targets the final decoder layer's attention output projection with LoRA. A separate local coding pilot recorded five updates in ten groups, with zero passes in both arms on 24 held-out tasks. This is implementation evidence with no measured gain in that pilot. [Qwen3 backend](../src/apple_harness_adapter/backends/qwen3.py)
- **Inkling 2 Mini.** The experimental 4-bit looped backend targets the last attention output projection of the loop core. It uses reference operations, detaches the discrete top-k expert selection, and keeps the gathered and normalized sigmoid weights differentiable. Uncached scoring can checkpoint decoder visits. Cached scoring captures attention K/V and convolution state at selected boundaries, recomputes spans during the backward pass, and uses MLX vector-Jacobian products to propagate gradients through the cache and back into prompt prefill. It halves the decode block size when the score drifts beyond tolerance, down to one token, and uses the accepted block's gradients. Local rehearsals and tests exercised these paths. The held-out release result uses LFM3 only. [Inkling routing](../src/apple_harness_adapter/backends/inkling.py) · [Cached backward pass](../src/apple_harness_adapter/backends/inkling_score.py)

### Checkpoint recovery

The runner saves the adapter after each update and the optimizer state and sampling key after each group. It commits the group with an atomic rename of `metrics.json` after the tensors are saved. On resume it checks run settings and checkpoint state, restores the latest committed state and most recent updated adapter, archives an unfinished group, and collects that group again. A new run initialized with an adapter starts with fresh Adam state. [Checkpoint implementation](../src/apple_harness_adapter/checkpoint.py)

## Reference experiment

Warmup used two calibrated tasks from two source datasets, cycled across three eight-attempt groups with seed 81. Main training used 14 new tasks from 14 sources, cycled across 50 eight-attempt groups with seed 1229. The main run initialized from the warmup adapter with fresh Adam. Of 64 staged main-training candidates, the calibration run tried 44 and selected the 14 yielding mixed verifier outcomes over four attempts with the warmup policy. Learning rate was `1e-5`. The main checkpoint evaluated here is group 50, after optimizer step 41. [Run provenance and settings](../results/lfm3-pi/provenance.json)

The reported held-out split came from the pinned SmolDataEnvs registry at indices 1000 and above, using selection seed 8112029. Selection excluded source datasets from all earlier local LFM3 task manifests, including warmup, calibration, and earlier evaluation. It used easy and medium tasks with one to three allowed input files and at most 16 MiB of inputs. Selection used task metadata and offline staging checks. The final sample was 43 easy and 107 medium tasks across 93 sources, with up to three tasks per source. [Frozen selection and input hashes](../examples/smoldataenvs/heldout.jsonl)

The original evaluation ran one attempt per task per arm. All arms shared the pinned BF16 model, Pi 1.5.2, the same task image and verifier, temperature 0.8, low reasoning effort, a 6,144-token context limit, at most 1,024 output tokens per request, and up to ten turns. Agent and verifier timeouts were 150 and 30 seconds. Each task used seed `7297 + zero_based_task_index` for every arm, and evaluation order rotated through all six permutations of base, local, and the converted published Harness Hub Pi adapter. The public two-arm recipe alternates base-first and adapter-first. [Paired measurements and original order](../results/lfm3-pi/pairs.jsonl) · [Current reproduction recipe](../examples/smoldataenvs/README.md)

A pass is a verifier score of 1. The accuracy estimate is the difference between arm pass rates in percentage points. Shared-success tool-call change is `100 × (adapted calls / reference calls − 1)` using totals over tasks both arms passed. This conditions on joint success, so each comparison can use a different subset. The source-dataset bootstrap draws 93 clusters with replacement for each of 10,000 resamples (seed 8921), retaining paired outcomes and all tasks in the sampled clusters. It recomputes task-weighted pass-rate change and the joint-success call ratio in each draw. Draws with zero reference calls are omitted for that interval. Bounds are the 2.5th and 97.5th percentiles using Python's exclusive quantiles. The accuracy interval includes zero. [Analysis and full comparison results](../results/lfm3-pi/README.md)

The host was a Mac Studio with an Apple M4 Max and 128 GB of unified memory. The main phase took approximately eight hours, including collection and optimization. The 35.526 GiB peak is MLX's allocator measurement and excludes the rest of macOS and Docker. The paired evaluation's maximum recorded MLX allocation across all three arms was 19.927 GiB. Package versions, historical engine hashes, timeout settings, and artifact hashes are recorded in the audit. [Hardware and software provenance](../results/lfm3-pi/provenance.json)

## Limitations

The release result comes from one training run on 14 main tasks and a stochastic evaluation with one rollout per arm per task. The intervals describe uncertainty under source-dataset resampling in this holdout. Across-seed and across-training-run variation remain unmeasured. The data-analysis QA tasks and difficulty selection limit generalization to other distributions, models, and harnesses. This checkpoint has no broad coding-benchmark validation. Shared-success tool calls measure one aspect of efficiency. Token consumption, latency, energy, and end-to-end compute cost require separate measurements.

The frozen manifests support repeating the schedule and task selection. The current Pi runner and image preparation evolved after the historical experiment. The frozen engine hashes show changes in the CLI, checkpoint helper, Harbor integration, and relay relative to Git commit `053ad0f`. Stochastic sampling and rebuilt containers can also change outcomes. Replaying the released measurement statistics is deterministic. [Results and reproducibility scope](../results/lfm3-pi/README.md)
